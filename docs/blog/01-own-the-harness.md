# 01｜我们为什么保留自己的 Harness，却不再维护模型协议

Agent Engineering / oh-my-quant · 初稿 2026-10-12 · 修订 2026-10-14 · 架构与演进

连接模型、注册工具，可以让量化 Agent 开始回答。要让它在取消、配置变化和报告恢复之后继续正确工作，还需要决定：谁为一次研究的完整生命周期负责。

## 接入内核之后，应用还应该拥有什么？

Pi 已经提供模型协议和低层执行循环。复用它，意味着 oh-my-quant 不必自行追赶每种供应商的流式格式、工具调用协议与模型目录。这是明确的收益，也让「尽量采用上游能力」成为合理起点。

但量化研究的状态比一次模型调用活得更久。用户会在工具执行时补充问题，会修改模型连接，也会打开昨天的报告，要求从当时的分支继续。内核能运行工具，不代表它知道这些动作该怎样改变 WhyJ 的研究状态。

Lilian Weng 用 planning、memory、tool use 建立了 Agent 的能力地图。构建应用时，我们需要在这张地图上再标出所有者：谁准备资源，谁提交状态，谁在失败后保住当前工作。[LLM Powered Autonomous Agents](https://lilianweng.github.io/posts/2023-06-23-agent/)

## 最后一个 token，不是研究的终点

只沿着调用链看，模型返回最后一个 token，操作似乎就完成了。但结果可能尚未落盘，监听器还在运行，用户此时又发起了恢复。若 `busy` 只覆盖流式输出，准备和收尾阶段就可能失去保护，旧结果也可能写入已经切换的分支。

把这些规则全部放进模型回调，能够就地处理问题，却会让协议适配承载越来越多产品语义。反过来，把整个循环复制到项目里，虽然获得了修改自由，也把供应商兼容与后续升级变成自己的长期责任。

因此，这不是「要不要模块化」的抽象选择，而是两种变化是否应该由同一层承担。模型协议变化，与研究分支、报告恢复规则变化，并没有相同的节奏。

<a id="ownership"></a>

旧重构路线也曾提出分阶段拆分。重新核对时，我们发现“文件更短”和“模块可替换”被放得太近了：前者可以靠移动代码完成，后者却需要一个不依赖默认本地宿主的真实实现来验证。因此保留的是先治理依赖、再按变化压力抽服务的顺序，不是旧 P0–P3 文件清单。目录结构是结果，不能替代对所有者和副作用的判断。

## 复用循环，把领域生命周期留在应用侧

现在，`kernel/loop.ts` 接入 Pi 循环，`kernel/llm.ts` 接入模型协议与目录；WhyJ 的 `session-runtime` 管理队列、分支、压缩与操作生命周期。`QuantAgentSession` 接收模型、工具、技能、存储和核验端口，TUI 订阅状态，不直接编辑会话树。

![Pi 与 WhyJ 的职责边界：协议和循环位于内核，操作生命周期、研究状态和报告位于应用层。](./images/01-harness.svg)

*图 1：协议复用没有消除应用状态；边界把两类变化分开。箭头是调用或数据流，不表示独立部署。*

在 Harness 内，一次操作包围资源准备、执行、持久化和需要等待的监听器。概念上，它比一次模型请求更长：

```ts
const finish = operation.start("turn");
try {
  const resources = await prepare(operation.signal);
  await run(resources, operation.signal);
  await flush(); // 收到最后一个 token 后，仍须完成必要的提交。
} finally {
  finish();
}
```

这段示意不是现有实现的替代代码，也不是一个覆盖所有入口的事务。`QuantAgentSession.prompt()` 在进入 `harness.prompt()` 前还会同步模型、技能和研究投影；`waitForIdle()` 等待 Harness 操作，不保证 facade 全部前置工作都已串行化。这个缺口应该明确留下，不能因为有了 `HarnessOperation` 就宣布并发问题全部解决。

配置更新采用相同的思路：独立 prompt、skill 和手动压缩准备连接快照；在途循环与排队续问保持原连接。工具和技能在允许的空闲边界更新，准备失败保留旧资源。否则，一次请求可能使用旧 endpoint，却在下一步读到新 key。

迁移曾让这个边界暴露得更具体：更新依赖版本并不意味着请求已使用新协议，旧路径别名仍可能把调用导向本地副本；Pi 的 TranscriptContext 也要求摘要入口一起迁移。只修主对话而不检查压缩，是把“能开始回答”错当成“整个会话已经升级”。现行版本因此只从依赖声明读取，升级核对的是入口与行为，而不再由几篇文档各自记一个版本号。

事件也是同样的陷阱。读取流式事件能看见 assistant 输出，却不天然阻止下一步工具执行；如果落盘还在异步队列里，任务守卫就可能读到旧分支。现在用可等待的事件 sink，把 assistant 提交完成放在工具预检之前，并用故意延迟提交的回归验证顺序。代价是持久化进入关键路径，换来的是守卫有明确的事实读取点，而不是“事件大概已经处理了”。[消息屏障回归](../../src/agent/test/kernel.test.ts)

我们因此放弃了「所有动作立即切到最新配置」的直觉，选择「一次操作使用可解释的资源版本」。取消也一样：abort 只是发出停止请求，摘要提交、leaf 移动和状态发布前仍要核对操作有效性。

## 可替换的边界，也有维护成本

已有独立宿主回归用内存 repo 和自定义工具运行真正的 Pi 循环。它证明会话端口可以被实际替换，不只是接口定义允许替换；但这不证明所有模块已经独立发布，也不证明并发入口已经完全事务化。[会话依赖注入与验证](../agent-runtime/README.md#dependencies)

从维护角度看，这次选择有一笔不能省略的账：

| 路径 | 主要收益 | 留给团队的责任 |
|---|---|---|
| 自己维护协议与循环 | 最大修改自由 | 供应商差异、协议演进、兼容测试 |
| 全面采用上游应用运行时 | 减少本地生命周期实现 | 将研究分支与报告契约迁入其状态模型 |
| 当前的内核复用、应用运行时自有 | 两类变化相对分离 | 适配层、事件映射、取消与恢复回归 |

Pi AI / Agent Core 的具体版本以 [依赖声明](../../package.json)为准，升级仍需要验证类型、事件映射与完整生命周期，不能把“版本号已更新”当作迁移完成；WhyJ 也没有因此兼容 Pi 原生 ExtensionAPI。[内核适配边界](../agent-runtime/README.md#pi-integration)

文档也需要遵循同一边界。[Agent Runtime 设计](../agent-runtime/README.md)解释怎样执行、取消和提交；[Quant Harness](../quant-harness/README.md)解释完整量化应用：数据、计算、执行、报告和 UI/UX，以及它们如何共同约束研究范围、证据与接受条件。两者共享会话，不代表模型协议适配应该知道某个量化公式，也不代表“会话空闲”能够证明研究完成。两类文档分别落在 `docs/agent-runtime/` 与 `docs/quant-harness/`；目录区分的是通用机制与完整应用，不宣称代码已经拆成独立发布包。

这次文档淘汰提醒我们：旧设计曾经正确，不代表旧目录和版本还应约束现在。值得留下的是选择依据，以及何时应该推翻它。如果未来上游运行时能承接现有分支、取消与报告契约，并实质降低长期维护成本，就应重新评估这条边界。保留自己的 Harness 是当前选择，不是需要捍卫的身份。
