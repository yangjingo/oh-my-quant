# Agent Engineering：oh-my-quant 的产品、架构与体验

一个量化研究 Agent，应该对什么负责？

它需要拿到数据、解释结果，也需要说清数据来自哪里，保存当时的输入，在会话被压缩或切换之后恢复研究，并在能力不足时留下可理解的失败。oh-my-quant 的演进围绕这个问题展开：如何把模型的一次合理回答，放进一个有明确状态与证据边界的应用里。

这组中文文章面向**技术负责人和 Agent 应用架构师**。除了可靠性，还讨论产品为什么围绕研究工作流组织、技术边界如何承接变化，以及用户如何在有限屏幕里发现动作、理解状态和处理失败。从原方案的合理性出发，说明什么反例迫使它变化，再交代新选择解决了什么、增加了什么成本。每篇围绕一个具体问题沿因果推进，结果回到证据，不把迭代写成一路正确的故事。

阅读线有意交叉：产品承诺约束技术边界，技术状态最终要由界面解释。每篇均提供机制图、实现索引与后续判断条件，不为三个领域各写一份重复的系统介绍。

设计正文实际归入两个目录：[Agent Runtime](../agent-runtime/README.md)负责通用执行与会话生命周期，[Quant Harness](../quant-harness/README.md)负责完整量化应用，包含数据、计算、执行、报告、产品和 UI/UX。任务约束与证据核验是 Quant Harness 的核心机制，不是其全部范围。系列文章解释取舍，不替代现行契约，完整归属见[文档目录](../README.md#design)。

## 如何阅读证据

01–07 初稿基于 **2026-10-12 的工作区**，于 **2026-10-13 修订叙事**（01、07 于 2026-10-14 再次校正文档边界）；08–12 于 **2026-10-13 新增**，补齐产品、技术架构与 UI/UX 的设计判断。08 于 **2026-10-15** 更新为 Desktop-first 与两端共享研究事实的演进计划，明确区分当前 PTY 宿主、已选择的维护方向和未实施的 apps/workspace 改造。旧稿、归档和独立决策账已删除；错误判断、修正原因与代价直接进入各篇正文，不再要求读者跳到另一层历史汇编。

文章不是已发布版本说明，也没有把历史测试改称本轮运行成绩。代码链接定位实现，测试链接定位可重复检查，带日期的例子只说明当时观察。少量原始回执链接指向本地 `output/`，不随克隆保证存在，也不作为网站默认发布素材；正文保留理解反例所需的输入、错误与边界。架构建议、产品效果指标与重新考虑条件是分析或待测项，不是已经达成的结果。删除的理由与损失见[第七篇](./07-artifacts-and-boundaries.md#documentation)。

全部配图是本系列的本地 SVG，画的是机制、工作流或布局优先级，不是实测性能图或真实终端截图。十二篇正文以 Markdown 维护，HTML 是同一份内容生成的离线阅读视图，没有第三方脚本、字体或图片请求。

~~~bash
bun run docs/blog/build.ts
bun run docs/blog/check.ts
~~~

第一条从正文和 SVG 生成单文件 HTML；第二条核对本次整理涉及的链接、正文分节、修订日期和配图。结构检查不判断论证质量，独立读者复核另行进行；验证范围见[编辑与证据说明](./editorial-notes.md)。
