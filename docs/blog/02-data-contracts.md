# 02｜一次数据源故障，为什么需要三种成功定义

Agent Engineering / oh-my-quant · 初稿 2026-10-12 · 修订 2026-10-13 · 配置、能力与数据

一条用户反馈是这篇文章的起点：切换到 Tushare、保存 key 后，面板和状态栏没有同步，Agent 仍然报告 `daily_basic` 权限不足。用户的怀疑很直接：配置是不是根本没有改过来？

这条反馈暴露的不只是一条取数路径，还包括系统怎样向用户解释「成功」。

## 保存了数据源，为什么还不能确认它在工作？

配置保存、界面显示和工具执行，原本应该描述同一个应用状态。它们也确实各有职责：设置编辑器保存用户意图，面板投影状态，工具通过供应商接口取得数据。

但当三者给出相互矛盾的信号时，一条权限错误无法独立定位原因。可能没有读到新配置，可能端点仍然使用旧凭证，也可能配置已经生效，只是账户没有这项接口权限。仅凭这句话，既不能判定配置失败，也不能确认账号问题。

用户问「Source 和 Tool 是隔离的吗」，其实是在追问配置能否穿过我们的架构边界。职责可以分开，配置传播不能因此断开。

## 一个“成功”，承载了三个承诺

<a id="diagnostics"></a>

保存成功只证明某份设置已经提交。某次请求成功，只证明选定连接在那个市场、标的和窗口返回了有效样本。研究完成，还要求输入与任务范围、参数和计算方法匹配。

这些条件有关联，却没有替代关系：key 存在不能证明有接口权限，HTTP 200 不能证明有有效行，拿到价格也不能证明研究结论正确。

原来的紧凑快照路径还引入了一个不必要的条件：为了展示价格，调用了 `daily_basic`。于是，一项价格展示被绑定到更高权限的接口上。即使配置传播正确，用户仍可能失败；只修状态栏，并不能消除这项能力依赖。

而若让取数自动回退到别的供应商，再把原数据源标为可用，又会制造另一种误导：研究拿到了数据，却没有证明用户刚配置的连接能够工作。

## 连通配置，拆开保存、诊断与研究

WhyJ 在 `runtime/data/source-runtime.ts` 组装数据路径：读取设置、准备 provider 凭证、绑定缓存和归档，再调用 Source。Tool 负责模型可理解的输入输出，Source 负责标准化与回退，Storage 负责文件生命周期。Source 不必为了读取 key 反向依赖应用存储。

当前保存的配置覆盖相应环境值，显式调用选项通过端口传入，数据搜索也经过凭证加载入口。设置提交后的界面同步由 runtime 发布；设置来源与一次请求实际命中的 provider 仍须分开表达，后者可能经过回退。

快照工具则收缩了自己的承诺：复用 bars 的最新 OHLCV，不再为紧凑价格展示额外依赖 `daily_basic`。这同时意味着它不承诺 PE、PB 或市值。去掉一个权限依赖，并不是保留所有字段的免费优化。[快照工具实现](../../src/tools/data-tools.ts)

*图 2：共享 adapter，不共享成功标准。A/B 是示意 provider，不代表某次真实检查已经通过。*

普通研究可以按允许的策略回退，并返回实际 provider 与日期；Doctor 则固定连接、单源和请求窗口，不读缓存、不跨 provider 回退，也不放宽窗口寻找旧数据。AKShare 的成功不能替 Tushare 的权限背书。

配置编辑也据此拆开：数据草稿先检查，再显式保存与检查证据匹配的版本；模型 Save & Verify 不顺带保存数据草稿。用户修改参数后，旧检查不能继续替新草稿背书。

| 动作 | 可以宣布什么 | 仍然不能宣布什么 |
|---|---|---|
| 保存 | 这一版设置已提交 | 所有相关接口都有权限 |
| 单源诊断 | 指定请求取得了有效样本 | 其他端点、日期、市场同样可用 |
| 研究验收 | 显式条件已有匹配证据 | 模型所有解释正确、策略能够盈利 |

## 少一个权限依赖，多一份判断责任

配置绑定、单源探测与草稿检查都有对应实现和回归入口。它们让「哪份设置被使用」「哪个请求得到什么证据」成为可检查的问题，但本次博客修订没有重新调用用户账户，不能据此宣布其 `daily_basic` 权限已经恢复。[诊断契约与回归](../agent-runtime/configuration.md#diagnostics)

现有 API 还留下一个不够直观的地方：envelope 的 `ok`、报告级 `ready` 或退出码可能只表示诊断报告生成完成。自动化消费者仍须读 `overall` 和各阶段状态，因此 `ok: true` 与 `permission-denied` 可以同时出现。拆开语义改善了可解释性，却也增加了消费端的判断责任，不能把它写成已经完美统一的接口。

取得数据之后，还有「究竟是哪一份」的问题。Bars 和基金 NAV 使用固定版本引用，研究重读指定 DatasetRef，缺档不拿最新缓存替换。但本地观测时间不是供应商发布时间，今天获取去年的数据，也不能证明去年当时已经知道这些数据。[存储与时间边界](../agent-runtime/storage.md)

回头看，旧 Doctor 草图把配置、工具和数据放在一张诊断面板里，这个组织方式可以保留；把配置存在、流程结束和能力可用压成一个成功标签的判断，却必须纠正。验收单位因此从「接入 Tushare」缩小到「这份配置、这个端点、这个窗口的有效响应」。单源检查会暴露普通回退掩盖的失败，也让用户多做一步验证；这是为了获得可解释的失败归属而接受的成本。

重复面板草图不再保留，自动修复、后台巡检、全供应商扫描也没有因为出现在旧设想里就成为现有能力。后续若统一退出码与总体状态，必须同时迁移 CLI、面板和自动化消费者，不能只改一个绿色标签。
