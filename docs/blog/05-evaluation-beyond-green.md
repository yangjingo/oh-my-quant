# 05｜测试全绿，为什么仍然不能交付一个结论

Agent Engineering / oh-my-quant · 初稿 2026-10-12 · 修订 2026-10-15 · 评测与质量投资

2026-09-14 的核验记录里，有两个事实同时成立：调整后的项目测试 691 项通过；独立回测探针仍算出了错误权益。绿色结果没有撒谎，它只是没有检查这些数值契约。

## 什么证据足以支持一个研究结论？

测试首先帮助我们确认程序行为：参数校验、工具调用、状态提交和页面渲染是否符合预期。Agent 应用还需要确认外部请求是否可用、模型是否选择正确工具，以及最终文字是否忠实于结果。

这些工作都可以叫验证，但不能因此合成一张没有边界的成绩单。模型正常结束，不等于研究条件满足；研究条件满足，也不等于每个解释都正确。

技术负责人真正需要知道的是：某个通过标记排除了哪类错误，又留下了什么未知？

## 绿色勾选之外，反例依然存在

<a id="counterexamples"></a>

那次回测探针采用零费用、价格 100 → 100 → 110、本金 100000 的简单输入。1000 股涨到 110，应得到 110000，函数却返回约 111000。另一个 +10% / −10% 的探针，累计收益约为 −1%，CAGR 却是 0。这里保留的是 2026-09-14 的失败观察，不是本轮重跑结果；旧汇编已删除，现行口径和可重复反例分别进入[计算契约](../quant-harness/quant-tools-design.md)与[独立账本测试](../../src/quant/test/backtest-correctness.test.ts)。

这些反例不因为测试通过就消失。它们说明已有断言没有覆盖正确的账本和年化口径，而不是测试数量不够大。文档也曾沿用“初始名义本金且无现金约束”和统一 `252/N` 的年化简式；后来的实现已经采用现金、仓位账本与实际日历跨度，文字却没有同步。保留旧公式作为另一份规范，会让修过的错误重新进入读者的实现。

同类误判在回答层再次出现。2026-10-13 的一份对冲回答通过了当时九项自动检查，却把市值 9,240 相对成本 10,000 的亏损写成 240 / 2.4%；应为 760 / 7.6%。期限与预算单位检查改好了，并没有顺带证明情景算术正确。[本地原始回执](../../output/answer-followup-qualification-live-skill-risk-hedge-2026-10-13.json)保留旧的 9/9 和错误原文；它是内部历史样本，不是当前通过率或默认公开素材。

新闻评测则暴露另一层问题：引用 token 合法，句子的数字却来自其他段落；工具返回「复权口径未知」，回答却将其写成「未复权价格」。这一次，数据链路和输出格式可能都正确，错误发生在解释承诺上。

因子回归提醒我们，样本形状也会制造安全感。旧 RSI 递推重复消费了播种期末的变化，后续输出延迟一条；持续上涨时两版都可能是 100，错误藏住了。换成收盘 [10,11,12,11,10]、周期 2，正确末两项为 50、25，旧实现却是 100、50。SMA 差的另一处错误则把未形成的短均线当作零，短周期出现伪造的 −100%。增加更多单调样本不会替代这些转折和暖机反例。

评分解释也曾把 RSI 的贡献 16.00 写成最大，同表 IV rank 却为 19.50。原始分数最高和加权贡献最大被混为一谈；总分正确，并不能让这个解释自动正确。[原始套件](../../output/research-suite-final-34-2026-10-13.json)保留当时回答，本文不回写它。

项目还曾因默认测试发现范围过宽，混入参考仓库的 Vitest 测试和生成 Artifact 的演示脚本。于是连「哪些失败属于本项目回归」都不够清晰。先定义测试集合，再定义各层通过意味着什么，成为改进的前置条件。

## 把反例变成下一轮检查

测试围栏把默认发现根限制在 src，排除 `gen-*.test.ts`，演示生成器改用显式入口。`bun run test` 先检查围栏，再运行项目测试。它稳定了工程回归集合，却不是禁止一切网络和写入的沙箱；副作用仍需由 fixture 与测试设计约束。

![工程测试、真实服务样本、任务轨迹和回答主张分别进入评测；发现的反例回流到新的固定测试。](./images/05-evaluation.svg)

*图 5：每层验证支持不同声明；反例回流形成迭代，不是层层通过就得到普遍正确性的阶梯。*

| 证据 | 可以检查什么 | 不能替代什么 |
|---|---|---|
| 确定性工程回归 | 参数、取消、分支、账本、渲染 | 真实模型与供应商行为 |
| 真实服务样本 | 选定连接、端点和窗口的响应 | 长期稳定性与其他权限 |
| 固定任务轨迹 | 工具、参数、调用顺序、恢复取数 | 回答是否忠实解释结果 |
| 回答主张核对 | 已知数值、口径、引用与条件错误 | 未覆盖表达的人工判断 |

数值回归使用独立现金与股数账本，而不调用被测函数给自己生成期望值。在已定义的成交价格约定下，至少核对：

```text
cash[t] = cash[t-1] - tradeShares[t] × price[t] - cost[t]
equity[t] = cash[t] + positionShares[t] × price[t]
```

这些不变量可以检出一类实现错误，但不自动覆盖真实成交、停牌、滑点与复权规则。[独立账本测试](../../src/quant/test/backtest-correctness.test.ts)

六因子随后采用独立计算的 Latest 期望和末次下跌路径，每个验收条件绑定自己的调用、周期与窗口。旧 RSI 归档不重写；如果按修正后的公式无法重现，就撤销核验资格。这个选择牺牲了旧报告持续显示 verified 的便利，却避免把兼容性变成继续承认错误的理由。[因子方法与反例](../quant-harness/quant-tools-design.md#factor-methods)

显式评分则把用户给定的分数和权重交给无 IO 的算术工具，返回贡献、合计与并列最大项。它解决了这一层相乘与排名，不验证原指标怎样映射成分数，也不把高分解释为反转概率。[评分契约](../quant-harness/quant-tools-design.md#weighted-score)

<a id="answer-checks"></a>

回答层则从已经观察到的错误建立规则。2026-10-12 的新闻迭代增加明确口径断言检查，并在证据可匹配时识别已知冲突。交互 AppRuntime 保留错误原文、追加复核提示，并阻止本轮自动报告继续生成，而不是把错误悄悄改成一份看似干净的报告。[回答证据与门槛](../quant-harness/news-research.md)

这还要求检查器接受反例。限定语和否定句曾被当成正面断言；离线修改规则后，旧回答不再触发告警，只能说明重检结果改变，不能把原来的失败回执改成一次新的模型成功。反过来，引用格式有效、九项检查齐全，也不能抵消一句错误的数字解释。年报、基金比较与因子年化各有证据条件，不能共用一个没有任务边界的“回答正确”标记。

对那份对冲错算，后续实现增加了无 IO 的[持仓情景计算](../../src/quant/position-scenarios.ts)，并将[有限情景检查](../../src/runtime/evidence/hedge-scenario-answer.ts)绑定到显式股数、成本与收盘价。旧错句成为回归输入；检查只覆盖识别到的未对冲股票情景，不核验期权收益或任意自由文本。后续模型样本的股票算术正确，仍出现“protective put 的保费最高”这类缺少同条件报价支持的比较。旧失败、离线重检和新样本分别保留在[本地阶段回执](../../output/scenario-arithmetic-validation-2026-10-13.json)，本文没有重新执行这些验证，也不把修好算术写成完整解释验收。

Langfuse 的 Skill 评测文章把输入、轨迹、评分与迭代连接起来。我们采用的是让观测服务于可重复改进的思路；当前仍使用本地事件和评测回执，没有因为引用它就接入 Langfuse 服务。[Evaluating AI Agent Skills](https://langfuse.com/blog/2026-02-26-evaluate-ai-agent-skills)

## 修复一个错误，不等于得到总体正确率

回测权益和 CAGR 后续已有独立账本修复与回归，新闻检查也能拦截已知口径冲突。它们分别改善了确定的数值契约和有限的回答门槛，不应被合并为「研究质量全面提升」的数字。当前怎样复验，由[统一评测指南](../evaluation/README.md)维护；本文记录的是这些规则为何出现，不充当完整验收报告。

代价是验证本身也需要版本和边界。词法规则可能漏掉语言改写，合法引用不能证明句子与段落语义一致，人工审阅仍要发现新的错误类别。一次真实模型复测通过，也不能推出总体错误率下降了多少。

六因子的真实运行就是这个区别：数值已经正确，表头、中文逗号和编号标题仍使有限解析器误判；调整解析器后离线重读原文，只能更新重审结论，不能制造一次新的模型通过。同时，回答仍可能把均线差说成斜率，或对极小样本给出过强解释。源码快照与人工审阅分别留在[本地修订记录](../../output/quant-factor-final-freeze-2026-10-13.json)和[回答复核](../../output/quant-factor-production-review-2026-10-13.json)；旧 33 场景与新增后的 34 场景也不能拼接为同一总体成功率。

因此，一份回执要留下任务、输入、真实或合成环境、检查规则版本、失败回答位置，以及未验证项。成功率的分母也要固定：返回文字、完成工具、满足任务条件、人工确认解释正确，不是同一个事件。

文档清理在这里有一条硬边界：旧汇编可以删除，错误不能被改写成成功。我们把有解释力的失败与修正写进本文，把可重复输入放在测试、原始回执留在内部输出；没有把每次测试数量和运行日志重新搬成一本博客附录。代价是本文不再提供逐次运行的完整历史，追溯个别数字仍需对应原始回执。

工程回归本身也会偷带本机假设。2026-10-15 整理测试入口时，本地全量通过，但[干净 Windows CI](https://github.com/yangjingo/oh-my-quant/actions/runs/38603140139)暴露 Doctor JSON 的「提示必须为空」依赖预装 AKShare。后来把测试改为显式缺 Python，断言 Tools 失败原因与结构化回执，而不把联网跳过误当依赖已经就绪。同期首个同步子进程返回空退出状态：最初怀疑工作目录，固定入口后全量仍复现、单组却通过。这份反例没有证明 Bun 的具体根因；测试改为等待实际退出并读完输出，仍检查退出码和原 JSON 契约。[入口回归](../../tests/app/index.test.ts)维护可重复条件，完整发布门槛与最终提交 CI 仍须分别通过，不能把单组成功外推成整库成功。

对下一笔工程投入，我们更愿意从反例出发。缺数据就修数据链路，误读口径就改证据与解释检查，调用越界就审查资源装配。测试的价值不仅是让发布前多一个勾选，还在于让「下一步改哪里」有具体依据。
