# Community Tools：开放能力，不模糊责任

量化研究需要不断扩展的数据与方法，全部由应用内部维护既昂贵，也难跟上社区演进。但“能安装更多工具”并不自动意味着研究更可靠：技能描述可能超过实际权限，服务连接可能没有所需数据，第三方返回值也可能缺少本地核验所需的来源。

Community Tools 因此连接两类不同资源：Skills 提供可复用的研究过程，MCP 连接外部能力。两者都扩展应用，但不替代内置数据契约、任务范围或账户授权。

<a id="toolkit"></a>

## 方法与能力分开，才能知道失败发生在哪里

Skill 交付指令和相关资源，告诉 Agent 如何组织任务；MCP 服务交付可协商的工具或上下文。一个选股流程可以存在，但它依赖的财务服务尚未连接；一个行情服务可以连通，但不意味着 Agent 已理解如何完成研究。

Agent Skills 的开放格式把领域知识与工作流组织成可携带资源；MCP 的架构则区分宿主、客户端与服务端的责任。[1][2] 本项目将二者接入现有 Pi 能力，不再另建技能解析器和 MCP 客户端，以减少协议升级时的重复维护。

应用负责预制目录、安装选择和接线；Pi 负责对应解析、加载或连接机制；上游作者负责方法与依赖的维护。预制目录不是独立质量认证，也不是对任意脚本、包或外部服务的审阅承诺。

<a id="installation"></a>

## 安装选择不能悄悄变成全部启用

下载一整个仓库方便缓存与版本管理，但模型不应因此看到其中所有技能。安装资源与选择加载项分开，用户可以只启用需要的方法；移除选择也不意味着删除本地源码与修改。

更新需要保护用户改动，准备成功后再发布新资源，失败或取消保留现有可用状态。应用不应在启动时自动拉取一批新技能，使同一个研究请求今天和明天看到不同工作流。

仓库通过内置 HTTPS 下载固定 commit 的 GitHub 压缩包，不依赖 Git 或 curl。预制技能采用目录中锁定的 commit；任意 `owner/repo` 先解析默认分支的 commit 再下载。安装收据 `.whyj-skill.json` 保存仓库、commit 和文件内容 SHA-256，更新前后核对修改、删除和新增文件；更新版本还须通过 GitHub compare API 的前进检查。已安装且未修改的相同固定版本可离线复用。仅所选技能进入加载配置，下载同仓库的其他文件不会自动启用它们。

下载先进入临时目录，校验完成后替换安装目录；拒绝路径穿越、越界链接、硬链接、大小写冲突及特殊文件；仓库内部符号链接只校验目标并跳过，不创建链接，所选技能入口必须是实际文件。元数据请求限时 60 秒，压缩包下载限时 180 秒，压缩包上限 32 MiB，展开上限 128 MiB、10,000 条目。公共仓库不要求令牌；私有仓库通过 `GH_TOKEN` 或 `GITHUB_TOKEN` 提供 Contents 读取权限，令牌只发给 GitHub API，不写入收据或转发到下载地址。安装依赖 GitHub 网络与 API 配额，不再使用本机 Git 凭据助手。

已有 Git 克隆或手动目录仍可加载，安装器不会改写或自动迁移这些目录。更新时需先将原目录移到受管 Skills 目录之外保存，再重新安装，随后按需合并自己的修改。新安装不保留 `.git` 历史；它是供加载的资源快照，文件内容校验不提供仓库历史或权限位审计。

这个选择增加了一步显式管理，却使能力变化具有可解释性。具体目录和安装操作由应用帮助维护，设计文档不复制随上游变化的技能清单。

<a id="discovery"></a>

## 资源刷新与在途研究使用不同时间边界

技能可以来自项目、安装缓存及显式启用的用户目录。发现时有确定的优先级，管理操作遇到同名歧义则需要明确对象，不能靠显示名称猜测修改哪个仓库。

加载后形成当前请求使用的资源快照。刷新成功只影响下一次独立请求，在途请求与排队续问继续使用原快照；否则一次研究可能前半程按旧流程取数、后半程按新流程解释，却没有任何可见分界。

代价是用户保存文件后不会立即改变正在运行的任务。界面需要说明刷新何时生效，而不是用立即切换换取表面响应速度。准备失败时保留旧资源，恢复与取消由[运行时](../agent-runtime/README.md#dependencies)统一协调。

<a id="mcp"></a>

## 连接配置不等于会话已经拥有能力

MCP 配置保存在哪个作用域、何时加载、使用哪份凭证，都属于连接边界。当前预制配置复用 Pi 的用户或项目配置；WhyJ 行情设置不自动复制到 MCP，也不会因为保存模板就自动启动一个外部服务会话。

项目覆盖与用户配置可能同时存在。删除项目项后，用户级同名服务可能重新可见，因此“移除这一项”不总等于“此服务在任何作用域都禁用”。这种行为需要明确说明，不能让界面动作承诺超过实际作用域。

外部进程包可能在客户端启动时才获取，HTTP 服务则依赖远端状态。连接成功、发现工具列表、执行公开样本与完成真实研究应分开判断；内置行情的检查不能代替另一条 MCP 路由的验证。

凭证与访问权限由目标客户端及服务维护，协议集成也不是隔离恶意代码的沙箱。MCP 架构强调宿主的权限与生命周期责任；本项目遵循这类责任分工，不据此声称所有第三方实现已经安全。[2]

## 接入社区结果，不降低研究的证据要求

第三方方法可以提供有价值的解释，但读取了一篇 Skill 并不产生行情证据。用户提供的材料应保留出处、日期、缺项与推断边界；模型不能用“工作流要求这样写”代替数据支持。

同样，能力可见不意味着允许使用。当前任务的对象、日期、工具范围与宿主权限继续约束社区工作流；任务不允许某项能力时，不能借技能文字绕开。新结果若尚未具备固定输入与重算规则，就应作为未核验材料，而不是自动满足量化任务的接受条件。

开放生态的价值在于让方法和服务容易替换，稳定的边界则让替换不会同时改变“成功”的定义。应用不为每个社区技能复制资格系统和执行规范；只维护共同的加载、能力、来源与研究验收接口。具体规则回到[研究编排](./README.md#tasks)和[数据层](./source-data-providers.md)。
