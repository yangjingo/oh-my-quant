# 执行：让研究与交易保持明确边界

研究可以提出买卖建议，却不能因此获得账户操作权限。执行层独立处理订单、授权与成交状态，避免一次研究完成、模型回复或报告生成被误当成交易指令。

当前仓库提供执行接口、本地模拟盘和 Alpaca Paper 适配器。它们支持检验订单流程；真实券商账户、真实成交和实盘服务尚未验收。默认研究 Agent 不加载账户与下单工具。

## 谁负责决定，谁负责执行

通用执行层只校验订单意图、约束调用顺序并核对回执。宿主选择账户、装配适配器、管理私有存储，并提供可信授权；适配器检查市场规则、可用资金、可卖数量和费用。这样，研究模型不需要持有交易凭证，通用接口也不会把某个市场的规则当成所有市场的规则。

订单必须明确指定账户、模拟或实盘模式、标的、方向、数量和价格，不能从当前界面或默认账户推断。现有接口只定义限价订单，不隐含市价、做空、杠杆或资金划转。数量和金额使用精确十进制运算；限价估值上限约束数量乘价格，不含手续费，不能代替账户资金检查。

预检绑定完整订单意图及有效期。实盘授权还绑定提交或取消动作，由宿主回调提供，不能由模型填写一个“已授权”字段代替。等待确认后要再次检查账户目标和有效期；修改数量、价格或账户后，旧确认不再适用。接口中的摘要用于绑定内容，本身不是身份认证或安全沙箱。

## 结果不确定时，先查单

执行最难处理的不是明确失败，而是请求已发出、回执没有到达。此时再次下单可能造成重复交易，因此流程必须区分：

- **尚未提交**：校验、预检或授权失败，可以修正输入后重新发起。
- **已收到订单回执**：核对账户、订单身份、数量和成交明细；收到回执不等于已经成交。
- **需要对账**：提交调用后的超时、异常、取消或非法回执，保留原订单 ID 与意图查询，不自动补单。

订单 ID 在适配器、账户和模式内唯一。相同 ID 与相同意图应对应同一逻辑订单，换了意图则拒绝；这要求适配器跨并发、跨重启保存去重状态，进程内缓存不够。通用层每次调用最多提交一次，但不能替外部服务承诺“恰好执行一次”。

例如，用户确认一笔限价买单，服务已接收，客户端却在收到回执前断线。如果把超时解释为未提交并生成新订单，就可能买入两次；如果永远禁止继续，又会让用户无法恢复。接口因此把不确定状态作为正式输出，要求沿原身份查询。AWS 关于幂等 API 的讨论同样区分请求标识与请求意图；这里借鉴的是重试的设计问题，并不据此证明券商具备同样保证。[1]

查不到订单只表示尚未观察到记录，不能推断它没有执行。停止等待也不能撤回已经发出的请求。撤单回执可能只表示请求已接收；最终仍可能已经成交，部分成交和费用必须保留。成交明细不完整或数量不一致时，不能把快照当成可靠结果。

## 私有账户不进入公开研究产物

账户、余额、订单和成交属于私有执行状态，不混入行情缓存、观察组合或自动研究报告。执行入口要求显式选择账户和私有目录；文件权限由宿主负责，不能用“私有”目录名称代替访问控制。

本地模拟盘另有显式启用的 Agent 会话，使用独立工具和会话记录；提交与取消需要宿主审核完整意图。这里的“独立”不代表离线：账户和订单工具结果会进入所选模型的请求及私有会话记录。用户必须知道数据会流向哪里，不能把与研究会话隔离理解为不向模型发送数据。

## 两种模拟实现，各自证明什么

**本地模拟盘**用于检查账户记账、资源占用、重复请求与恢复。它以文件锁和原子替换保存账本，开放订单占用相应资金或持仓；成交由宿主显式注入。它没有自动撮合、真实报价、交易所日历或公司行动，因此只支持持续有效的限价订单，不能用它证明策略可成交或交易收益可靠。

**Alpaca Paper**固定连接模拟交易地址，使用独立凭证与私有意图日志，目前限制为美元计价美股、整股、仅做多、持续有效的限价订单。发送前先保存意图占位；若进程中断，恢复时按原 ID 查询，不能因为暂时查不到就再次发送。

这个顺序主动承担了一个代价：即使中断发生在真正发出请求之前，系统也可能停在待对账状态，需要人工确认。相比猜测未成交后补单，当前设计优先避免重复执行。离线 HTTP 替身只能验证这些分支，不能证明真实账户权限、网络故障表现或券商成交行为。

后续接入真实执行服务时，需要验证其授权、持久去重与对账能力。接口接受完整意图，交付已知结果或待对账状态；账户与市场规则由适配器解释，可信授权与恢复决策由宿主管理。这个结构让研究能力可以继续扩展，而交易权限不随之默认扩大。当前接口和模拟结果不构成实盘交付证明。
